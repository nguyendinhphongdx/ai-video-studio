# Plan: Drizzle ORM, then Postgres

Status: steps 1–3 done (async data layer, Drizzle schema, repositories on Drizzle); steps 4–6 not started.

## Why

- The app keeps everything on one disk (`data/app.db` and `data/media`). Hosts whose disk does not survive a
  restart cannot run it: Cloudflare Containers, Fly, Render and similar.
- A managed Postgres (Neon, Supabase, RDS, …) plus object storage for media (R2/S3) removes that limit. Web and
  worker can then run as several copies.

## Choice: Drizzle ORM

- **Tables are defined in TypeScript.** Row types come from the schema (`$inferSelect` / `$inferInsert`).
- **One API for SQLite and Postgres.** The repositories move to Drizzle while the app still runs on SQLite, then the
  driver changes.
- **Queries stay close to the SQL we have now,** so the rewrite is mostly one to one.
- Migrations are generated by `drizzle-kit`.
- If we want entity classes later, MikroORM is the fallback. The repository boundary keeps that change inside the
  repositories.

## What there is today

| | |
|---|---|
| Driver | `node:sqlite` `DatabaseSync`, synchronous |
| Tables | 29 `CREATE TABLE`, append-only migrations in `src/server/db.ts`, tracked by `PRAGMA user_version` |
| Code that runs SQL | 14 repositories, plus `prefs.service`, `settings.service`, `media-access`, `health` |
| Transactions | `transaction()` in `db.ts` (`BEGIN IMMEDIATE`), used by `series.service` and `episode.repository` |
| SQLite-only SQL | 8 `ON CONFLICT` upserts (Postgres has them too), 3 `LIKE` (media access), JSON kept as `TEXT` |
| Job queue | `jobQueue.claimNext()`, safe today because SQLite has one writer at a time |

## Rules that stay

- `ctx()` gives `workspaceId` and `userId`. No connection or context passes through function parameters
  (AGENTS.md rule 9).
- Every query filters by `workspace_id` (rule 10). A small helper `scoped(table)` returns
  `eq(table.workspaceId, ctx().workspaceId)`, so each repository writes `where(and(scoped(episodes), …))`.
- Repositories are the only place that touches the database.

## Steps

Each step ends with the full test suite green and the app working. Each is its own commit.

### 1. Make the data layer async (still SQLite, no Drizzle) — done

The step most likely to break things, so it goes first and alone.

- Every repository function returns a `Promise`.
- Every caller adds `await`: services, route handlers, worker, outbox, tests.
- `transaction(fn)` becomes `async`.
- Turn on the ESLint rules `@typescript-eslint/no-floating-promises` and `require-await` to catch a forgotten
  `await`.
- Size: the largest step. About 3–4 days.

### 2. Drizzle schema matching today's tables — done

- `src/server/schema.ts`: all 29 tables as they are now (`sqliteTable`), generated from a database built by the
  current migrations. Column names stay snake_case in SQL; fields are camelCase.
- `src/server/orm.ts`: `orm()`, Drizzle on the same node:sqlite connection through Drizzle's `sqlite-proxy` driver
  (Drizzle has no node:sqlite driver, and `drizzle-kit pull` would need better-sqlite3).
- Node 22's node:sqlite returns rows as objects, so two result columns with the same name would collapse. `orm()`
  checks each query's column count (from `EXPLAIN`) and throws instead; such joins alias one column. This goes away
  with the Postgres driver.
- Changed from the first plan: the SQL `MIGRATIONS` in `db.ts` stay the source of truth until step 4. A Drizzle
  migration baseline for SQLite would be thrown away when Postgres gets its own. `tests/server/schema.test.ts` keeps
  the two in step (tables, columns, types, NOT NULL, primary keys, indexes).

### 3. Move repositories to Drizzle, one module at a time — done

- Every repository (and the few services and routes that ran SQL: prefs, settings, media access, health) queries
  through `orm()`. Raw `db()` is left only for migrations and the test context.
- `scoped(table)` is the workspace filter and `owner()` the workspace and person stamped on inserts.
- JSON columns stay TEXT, written with `JSON.stringify` and read with `json()`. Booleans stay 0/1 integers mapped in
  the row mappers. Both become `jsonb` and `boolean` in step 4.
- Raw `sql` only where it reads better: usage sums, the admin's workspace overview, `adoptOrphans` over the data
  tables, conflict updates that keep another workspace's row.
- Episodes load their scenes in one query for a whole list (was one query per episode).

### 4. Switch to Postgres

- Driver: `postgres` (postgres.js) with `drizzle-orm/postgres-js`. `DATABASE_URL` in `.env`.
- Schema moves from `sqliteTable` to `pgTable`. Types: `text`, `integer`, `boolean`, `jsonb`, `timestamptz` (today
  ISO strings).
- Job queue: `claimNext` uses `UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING *`. Several
  workers can then run at once.
- Transactions: `db.transaction(async (tx) => …)`. The current `tx` lives in the AsyncLocalStorage store, like
  `ctx()`, so repositories called inside a transaction use it without a parameter.
- Tests: each test file gets its own schema in one Postgres (Docker in CI), or uses PGlite in memory.
- About 2–3 days.

### 5. Media to object storage (R2/S3)

- A new `MediaPort` adapter on the S3 API. Uploads go to it; the app serves files through a signed URL or a proxy
  that keeps `canReadMedia`.
- Render temp files stay on the container's local disk. The finished video uploads to storage.
- Shared AI keys move from `data/settings.json` into a table.
- About 2–3 days.

### 6. Moving existing data

- `scripts/migrate-sqlite-to-pg.mjs` copies every table from `app.db` into Postgres in foreign-key order, then
  checks row counts.
- `scripts/upload-media.mjs` copies `data/media` to the bucket.
- Update `docs/DEPLOY.md`, `docker-compose.yml` (adds a `postgres` service for self-hosting) and `scripts/backup.mjs`
  (`pg_dump`).

## Total

About 2–2.5 weeks of work. Steps 1–3 are worth doing even if we stay on SQLite: async data access and a typed
schema.

## Risks

- **A forgotten `await`** in step 1: a write may not finish before the response, or an error goes unhandled. The
  lint rules plus the tests cover it.
- **Timestamps:** ISO strings compare correctly as text today. With `timestamptz`, any code that compares strings
  must compare dates instead.
- **Case-sensitivity:** `LIKE` is case-insensitive in SQLite and case-sensitive in Postgres. Check email lookups
  (stored lower-cased already) and media paths.
- **Hot reload in dev:** one Drizzle client on `globalThis`, the same way the context store is kept.
